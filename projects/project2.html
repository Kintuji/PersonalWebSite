Overview

Table for Two is a fast-paced co-op cooking game where players manage orders, prepare recipes, and coordinate under time pressure. Co-op cooking games live or die on one thing: does the chaos feel fair? If the order and timing systems don't hold together, the game either feels broken — orders lost, timers desyncing — or feels boring because it's too forgiving to create real pressure.

The Problem

Keeping order state fair under co-op chaos

Two players are moving fast, orders are stacking up, and either player can pick up, drop, or hand off an order mid-prep. The core challenge wasn't the cooking mechanics themselves — it was building an order and delivery system that could scale with unpredictable player behaviour without losing state or feeling unfair to whoever ended up holding an order when the timer ran out.

The trickiest edge case: if a recipe timer and a customer's patience timer both affect score independently, it's easy to double-penalise the player, or to score an order as "late" when it was actually handed off cleanly between the two of them.

My Approach

Order state as its own system, not attached to a player

I built the order/delivery pipeline as its own system rather than bolting order logic onto individual recipe objects. Each order carries its own timer, decay curve, and delivery state independent of which player is handling it — so a player can drop an order mid-prep, the other player can pick it up, and the timer and score decay keep tracking correctly without either player needing to "own" the order in code.

For customer behaviour, I drove both the visual state (waiting → served → leaving) and the scoring off a single customer state machine with a decaying patience value, instead of maintaining separate systems for "how the customer looks" and "how the customer scores." That single source of truth is what resolved the double-penalty problem above: one decay curve owns the lateness signal, and the delivery and customer systems both read from it rather than keeping their own clocks.

Result

A system that holds up under co-op pressure

The order/delivery and customer systems hold up under the kind of fast, uncoordinated play a real co-op session produces, and new recipe types can be added without touching the underlying timer or scoring logic. Playable build available on itch.io, with a full gameplay trailer above.

What I'd improve next

The UI / game-state sync layer currently does more manual bookkeeping than I'd like — it works, but it's the part most likely to break as more recipe types get added. Next step is moving that to a proper event-driven update instead of polling state every frame.
