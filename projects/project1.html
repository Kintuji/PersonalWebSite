Overview

Nexus of Warriors is a combat-focused project built around For Honor-style directional attacks, abilities, and enemy reactions. The goal was combat that feels readable and responsive on both sides — the player needs to see and react to enemy attacks, and the enemy needs to react to the player's in a way that doesn't feel scripted or exploitable.

The Problem

Enemy reactions that scale with attacks and abilities, not against them

With multiple attack directions and multiple abilities, the naive approach — a hand-written reaction for every attack × ability combination — doesn't scale. Every new ability added would mean touching every enemy reaction state, which gets unmanageable fast and is exactly the kind of coupling that makes combat systems fragile to extend.

The system also had to stay readable for the player: an enemy playing an animation that doesn't match what it's actually about to do breaks trust in the combat, so the FSM states driving behaviour had to line up with the states driving animation and hit windows.

My Approach

Attack events the enemy FSM reacts to, not per-ability logic

I built enemy behaviour as a finite state machine driven by attack events rather than attack types — when the player triggers an attack, it broadcasts an event with direction and timing data, and the enemy FSM decides how to respond (block, react, retaliate) based on its own current state and that event, rather than needing a case written for each specific ability. New abilities plug into the same event pipeline instead of requiring new reaction code.

Combat interactions (hit detection, stagger, retaliation windows) were handled as their own layer that both the player and enemy FSMs read from, so the same rules that make an enemy's attack land also apply to the player — one combat model instead of separate player-side and enemy-side logic.

Result

Enemies that react, not just execute animations

Enemies respond to player attacks and abilities through the shared event pipeline rather than scripted per-encounter logic, and new abilities didn't require touching enemy code — just emitting events on the same interface the FSM already listens to.

What I'd improve next

The FSM works well for the current move set, but as the number of enemy states grows, a behaviour tree (or utility-based layer on top of the FSM) would make it easier to add nuance — like an enemy choosing to disengage instead of always reacting — without the state count exploding.

My Contributions

  • Built FSM-driven enemy behaviour reacting to a shared attack-event pipeline
  • Implemented attack event responses (block, react, retaliate)
  • Worked on combat interaction logic (hit detection, stagger, retaliation windows)
  • Programmed gameplay abilities that plug into the same event system

Technical Focus

Finite state machines, event-driven combat architecture, hit/response timing, and ability systems designed to extend without touching enemy AI code.
